## 1. Стиль кода (5 правил)

| Правило | Плохой код (Bad) | Хороший код (Good) |
| :--- | :--- | :--- |
| **Snake_case** | `userId = "1"` | `user_id = "1"` |
| **Типизация** | `def add(a, b):` | `def add(a: int, b: int) -> int:` |
| **Константы** | `rate = 5.0` | `DAILY_FINE_RATE = 5.0` |
| **Импорты** | `from common.models import *` | `from common.models import Book` |
| **Пробелы** | `x=y+1` | `x = y + 1` |

## 2. Примеры поисковых запросов

* Запрос: "пушкин" -> Надет: "Капитанская дочка" (А.С. Пушкин).

* Запрос: "" (пустой) -> Вернет полный список книг.

## 3. Схема вычисления штрафа

Формула:
$$Fine = max(0, (Date_{return} - Date_{due}) \times Rate)$$

Где:
* $Date_{return}$ — фактическая дата возврата.
* $Date_{due}$ — плановая дата возврата.
* $Rate$ — сумма штрафа в день (например, 5 руб).
* Результат округляется до 2 знаков после запятой.

## 4. Ответы на вопросы

**1. Зачем вам единый стиль в таком маленьком проекте?**
* **Читаемость:** Даже через неделю я смогу быстро понять свой код, если он написан стандартно.
* **Привычка:** Соблюдение PEP8 тренирует профессиональные навыки для работы в больших командах.
* **Отладка:** Типизация (Type Hints) помогает IDE подсвечивать ошибки до запуска программы.

**2. Почему выбранная вами структура модулей уменьшает связность?**
Разделение на `client_gui`, `server` и `common` уменьшает связность (Loose Coupling), потому что:
* Логика вычисления штрафов (`utils.py`) отделена от интерфейса (`ui_screens.py`). Если мы изменим формулу штрафа, нам не придется переписывать код кнопок.
* Модели данных (`models.py`) лежат отдельно. И сервер, и клиент используют одни и те же классы, но не зависят от внутренней реализации друг друга.
