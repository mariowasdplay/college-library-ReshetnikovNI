# A6 — Качество, безопасность, реинжиниринг

## 1. Модель управления качеством

В рамках проекта «Колледж-Библиотека» качество определяется как соответствие функциональным требованиям (выдача/возврат) и надежность хранения данных (отсутствие потерь в CSV/JSON).

### 1.1. Цели качества
1.  **Корректность данных:** Система не должна допускать выдачу книги, если количество доступных копий (`available_copies`) равно 0.
2.  **Точность расчетов:** Штраф за просрочку должен рассчитываться с точностью до копейки по заданной формуле.
3.  **Отказоустойчивость:** Система должна корректно запускаться даже при отсутствии или повреждении файлов данных (создавать новые или игнорировать битые).

### 1.2. Артефакты контроля
| Артефакт | Назначение |
| :--- | :--- |
| **Unit-тесты** | Проверка функций расчета штрафа и генерации ID (`src/common/utils.py`). |
| **Логи (консольный вывод)** | Отслеживание ошибок подключения и обработки запросов API. |
| **Отчет о тестировании (CP7)** | Документальное подтверждение прохождения сценариев выдачи и возврата. |

### 1.3. Точки измерений
| Этап | Входные измерения | Выходные измерения |
| :--- | :--- | :--- |
| **Разработка** | Кол-во требований к API (4 маршрута) | Кол-во реализованных функций (4 функции) |
| **Тестирование** | Кол-во тест-кейсов (5 сценариев) | Кол-во найденных багов |
| **Эксплуатация** | Кол-во активных читателей | Кол-во ошибок при записи файлов (IOError) |

### 1.4. Критерии приёмки
1.  Сервер запускается без ошибок.
2.  Клиент подключается к серверу и отображает список книг.
3.  Цикл "Выдача -> Возврат" проходит успешно, данные сохраняются в `issues.json` после перезапуска.

## 2. Требования безопасности

Так как система является локальным прототипом, акцент делается на целостности данных, а не на защите от хакеров.

### 2.1. Роли и права
| Роль | Права |
| :--- | :--- |
| **Библиотекарь (Оператор)** | Полный доступ: поиск, добавление книг, выдача, возврат. Доступ к GUI. |
| **Система (Backend)** | Автоматическая запись в файлы, валидация данных, расчет штрафов. |

### 2.2. Защита данных
1.  **Валидация ввода:** Сервер проверяет наличие обязательных полей (`isbn`, `user_id`) перед записью.
2.  **Атомарная запись:** Использование временных файлов (`safe_write_json` в `io_utils.py`) защищает базу от повреждения при внезапном выключении питания.
3.  **Изоляция:** Данные хранятся в папке `data/`, отделенной от исходного кода `src/`.

### 2.3. Обработка ошибок
* **Пользователь:** Получает понятные сообщения в окне GUI (например, "Книги нет в наличии"), без технических кодов ошибок.
* **Система:** При сбоях JSON-парсера (битый файл) система не падает, а загружает пустой список, позволяя продолжить работу.

### 2.4. Базовые меры защиты
1.  Проверка типов данных (нельзя сдать книгу с датой из будущего).
2.  Запрет на дублирование ISBN при добавлении книги.
3.  Регулярный бэкап файлов `*.csv` и `*.json` (в ручном режиме).

## 3. Реинжиниринг процесса

**Выбранный подпроцесс:** Выдача книги читателю.

### 3.1. Текущий процесс
1.  Библиотекарь спрашивает ID студента.
2.  Библиотекарь ищет книгу в бумажном каталоге или Excel.
3.  Вручную записывает выдачу в журнал.
4.  Проверяет, нет ли у студента долгов (вручную листая журнал).

### 3.2. Улучшения

| Тип | Что меняем | Эффект |
| :--- | :--- | :--- |
| **Горизонтальное сжатие** | Убираем шаг "Ручная проверка долгов". Система сама проверяет долги при попытке выдачи (`api.py` -> `/issue`). | Сокращение времени обслуживания на 40%. Исключение человеческого фактора (нельзя выдать книгу должнику по ошибке). |
| **Вертикальное сжатие** | Объединяем "Поиск книги" и "Проверку наличия". При сканировании/вводе ISBN система сразу показывает статус (Доступно: 5/5). | Уменьшение количества действий библиотекаря. Снижение риска выдать книгу, которой физически нет на полке. |

## 4. Проверочные вопросы

**1. Какие 2 ошибки качества у вас наиболее вероятны именно из-за учебного формата?**
1.  **Отсутствие нагрузочного тестирования:** Мы не знаем, как поведет себя система, если в файле будет 100 000 книг (вероятно, будет тормозить поиск), так как проверяем на малых данных.
2.  **Слабая обработка краевых случаев:** Из-за сжатых сроков могли быть упущены редкие сценарии (например, одновременная выдача последней книги двумя операторами), что приведет к коллизиям в файлах.

**2. Какая одна мера безопасности даёт наибольший выигрыш при минимальной цене для вашей ИС?**
**Валидация входных данных на сервере.**
*Почему:* Простая проверка `if not isbn:` или `if copies <= 0` в коде API предотвращает разрушение структуры базы данных и логические ошибки. Это стоит 5 строк кода, но спасает от 90% проблем целостности системы.
