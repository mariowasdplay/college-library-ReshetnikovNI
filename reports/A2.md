# A2 — Модели ИС и SOA-вариант

## 1. Сравнение трёх архитектурных моделей

В таблице приведено сравнение Монолита, Клиент-Сервера (наш текущий выбор) и Микросервисной архитектуры (SOA) применительно к системе учета книг.

| Критерий | Монолит | Клиент–сервер (Наш проект) | SOA (Service-Oriented) |
| :--- | :--- | :--- | :--- |
| **Сложность внедрения** | **Низкая**: один файл или папка, база внутри. | **Средняя**: нужно запустить и Frontend, и Backend API. | **Высокая**: нужна настройка сети, API Gateway, брокера сообщений. |
| **Масштабируемость** | **Низкая**: копируется только целиком. | **Средняя**: можно запустить несколько серверов API. | **Высокая**: каждый сервис масштабируется отдельно. |
| **Обновление частей** | **Сложно**: любая правка требует пересборки всего ПО. | **Возможно**: можно обновить GUI, не трогая сервер. | **Легко**: сервисы независимы, можно переписывать их по одному. |
| **Надёжность** | **Средняя**: ошибка в одной функции роняет всё приложение. | **Средняя**: падение сервера останавливает работу всех клиентов. | **Высокая**: если упал сервис "Рекомендации", выдача книг продолжит работать. |
| **Нагрузка на сеть** | **Низкая**: всё внутри одного процесса. | **Средняя**: JSON-запросы между клиентом и сервером. | **Высокая**: постоянный обмен данными между сервисами ("болтливая" сеть). |
| **Простота отладки** | **Высокая**: есть один стек вызовов, легко ставить брейкпоинты. | **Средняя**: нужно смотреть логи сервера и клиента. | **Низкая**: сложно отследить путь запроса через 5 сервисов (Distributed Tracing). |
| **Стоимость сопровождения** | **Дешёвая**: нужен 1 администратор. | **Средняя**: поддержка API и версий клиентов. | **Дорогая**: нужна команда DevOps и мониторинг каждого сервиса. |
| **Гибкость (Changes)** | **Низкая**: "Спагетти-код" мешает изменениям. | **Средняя**: Четкое разделение ответственности. | **Высокая**: Можно написать новый сервис на другом языке. |

**Вывод:** Для нашей мини-ИС «Колледж-Библиотека» идеален **Клиент-Сервер**. SOA избыточна из-за сложности, а Монолит (без API) не позволил бы легко сделать мобильное приложение в будущем.

## 2. SOA-вариант: проектирование сервисов

Если бы мы переделывали библиотеку на SOA, мы бы выделили следующие независимые сервисы:

| Сервис | Назначение | Контракт (словами) |
| :--- | :--- | :--- |
| **Каталог книг (Catalog Service)** | Хранит информацию о книгах, авторах и наличии экземпляров. | `GET /books` — список книг.<br>`POST /books` — добавить книгу.<br>`GET /books/{id}` — детали книги. |
| **Управление читателями (User Service)** | Регистрация студентов, хранение их групп и статусов. | `GET /users/{id}` — данные студента.<br>`POST /users` — регистрация читателя. |
| **Журнал выдачи (Circulation Service)** | Главный бизнес-процесс: фиксирует факты выдачи и возврата. Общается с Каталогом. | `POST /issue` — выдать книгу (нужен ID студента и ISBN).<br>`POST /return` — вернуть книгу. |
| **Уведомления (Notification Service)** | Рассылка email студентам о просроченных книгах. | `POST /notify` — отправить напоминание (принимает ID юзера и текст). |
| **Рекомендации (Recommender Service)** | Анализирует историю выдач и советую книги (наш экспертный модуль). | `GET /recommendations?user={id}` — получить список рекомендованных ISBN. |

## 3. Проверочные вопросы

**1. Если завтра добавится «мобильная выдача», какая модель дешевле в сопровождении — и почему именно для ваших модулей?**
Дешевле будет модель **Клиент-Сервер (REST API)**.
*Почему:* У нас уже есть готовый API (`/books`, `/issue`), который возвращает JSON. Мобильному приложению нужно просто подключиться к этим же адресам. В Монолите пришлось бы переписывать логику под мобильную платформу, а в SOA накладные расходы на поддержку инфраструктуры слишком высоки для такой простой задачи.

**2. Какой один контракт в SOA вы бы сделали идемпотентным — и зачем?**
Я бы сделал идемпотентным контракт **`POST /return` (Возврат книги)**.
*Зачем:* Если библиотекарь (или автоматический сканер) случайно отправит запрос на возврат одной и той же книги дважды (например, из-за плохой связи), система должна обработать это корректно: первый раз вернуть книгу, а второй раз просто подтвердить успех, но **не увеличивать** количество доступных книг на полке лишний раз (+1 вместо +2).
