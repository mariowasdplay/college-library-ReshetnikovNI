# Отчет CP9: Отладка и обработка исключений, отладочные классы

## 1. Централизованная обработка исключений

Обработка исключений реализована на двух уровнях, чтобы обеспечить отказоустойчивость:

| Где перехватывается | Почему именно там |
| :--- | :--- |
| **На Сервере (Flask)** | Централизованный обработчик (`@app.errorhandler(500)`) перехватывает неожиданные ошибки в бизнес-логике (например, сбой при работе с файлами) и возвращает клиенту **500 Internal Server Error** с JSON-сообщением. |
| **В Клиенте (services.py)** | Блок `try/except requests.exceptions.RequestException` вокруг каждого сетевого вызова. Перехватывает ошибки транспорта (сервер выключен, нет сети) и переводит их в понятные сообщения для пользователя (`messagebox`). |
| **Отладочный класс/Миксин** | В модулях, таких как `storage.py` и `api.py`, применяется концепция **LoggerMixin** для трассировки выполнения сложных операций (валидация, запись), что помогает найти источник ошибки до её возникновения. |

## 2. Формат лог-строки

Для унификации отладки используется следующий формат лога:

```text
[TIMESTAMP] [УРОВЕНЬ] [МОДУЛЬ.ФУНКЦИЯ] <ID_ОПЕРАЦИИ>: Сообщение о событии/ошибке.

Пример лог-строки (ERROR)

[2025-11-22 15:30:01] [ERROR] [server.storage.load_data] <TXN_456>: Файл данных issues.json не найден.

3. Смоделированные ошибки
​Мы смоделируем 3 типа ошибок, демонстрируя, как система реагирует на некорректные входные данные и сбои.

3.1. Ошибка: Неверный формат JSON

Входные данные: Клиент отправляет на POST /issue тело без закрывающей скобки (невалидный JSON).

{ "user_id": "u001", "isbn": "978-5..."

Ожидаемый текст сообщения (для пользователя):
​Ошибка сервера: Неверный формат запроса (JSON). Пожалуйста, проверьте вводимые данные.

3.3. Ошибка: Отсутствующее обязательное поле

Входные данные: Клиент отправляет на POST /issue тело без обязательного поля user_id.

{ "isbn": "978-5...", "due_date": "2026-01-01" }

Ожидаемый текст сообщения (для пользователя):
​Ошибка данных (400 Bad Request): Отсутствует обязательное поле 'user_id' для выдачи книги.

4. Проверочные вопросы
​1. Покажите реальный фрагмент trace и объясните 3 строки логики происходящего.
​Предположим, Сервер не смог открыть файл books.csv:

Traceback (most recent call last):
  File "src/server/api.py", line 55, in issue_book
    storage.issue_book(data['user_id'], data['isbn'])
  File "src/server/storage.py", line 120, in issue_book
    inventory = load_data('books')
  File "src/server/storage.py", line 45, in load_data
    with open(f'{filename}.csv', 'r') as f:
FileNotFoundError: [Errno 2] No such file or directory: 'books.csv'

​Line 55 (api.py): Это точка входа в бизнес-логику. Здесь маршрут issue_book в API вызывает функцию из модуля storage.
​Line 120 (storage.py): Это точка сбоя логики. Функция issue_book пытается загрузить инвентарь (каталог книг), вызывая внутреннюю функцию load_data.
​Line 45 (storage.py): Это истинная причина ошибки. Здесь Python попытался открыть файл, но операционная система (ОС) вернула FileNotFoundError.
​2. Какие исключения нельзя «проглатывать» в вашем приложении и почему?
​Нельзя "проглатывать" (подавлять, перехватывать без повторной генерации) системные и фатальные исключения:
​SystemExit / KeyboardInterrupt: Эти исключения являются командами системы или пользователя на завершение работы. Если их перехватить, то программа не сможет нормально завершиться или отреагировать на Ctrl+C.
​MemoryError: Означает, что оперативной памяти недостаточно для выполнения операции. Попытка продолжить работу или что-то "залогировать" может привести к непредсказуемому поведению или дальнейшему повреждению данных. В таких случаях нужно немедленно прекращать работу.
